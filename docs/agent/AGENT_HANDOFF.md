## 1. Решение о делегировании

**Да, но выборочно.** Основание: проект один, но задачи различаются по связности.

**Оставляю ведущему (себе) — ядро, требующее сквозного понимания:**
- каноническая модель данных + temporal identity / roster resolution (`DATA-001`)
- **as-of evaluator** (вычисление признаков строго на cutoff)
- **immutable prediction snapshots + provenance ledger** (`API-001`)
- feature contracts и карантин данных
- calibration / backtest протокол

Причина: это differentiator d2intel, его нет ни в одном reference-проекте. Распараллеливание здесь создаст несогласованность временной семантики — главный риск проекта.

**Делегирую — изолированные задачи с чёткими критериями:**
- `INF-001` — скелет репозитория + smoke test (инфраструктура, не touching домен)
- `ING-001` — OpenDota-клиент: rate limit, retry, pagination, idempotence, raw capture (изолированный адаптер)
- вспомогательные: линтеры/CI, генерация документации, утилиты

Причина: чёткие границы, понятные acceptance criteria, минимальная связность с ядром.

## 2. Формат работы

### Роли
- **Lead** (этот агент): владеет архитектурой и временной семантикой. Формирует handoff-пакеты, ревьюит, интегрирует, ведёт документацию.
- **Worker** (суб-агент): получает одну задачу, работает изолированно, возвращает отчёт. Не принимает архитектурных решений.

### Цикл
1. Lead формирует **handoff-пакет**: контекст, задача, границы, acceptance criteria, `FILES EXPECTED TO CHANGE`, запреты.
2. Worker работает в **отдельной ветке** (`task/<TASK-ID>`), одной задаче — один агент.
3. Worker возвращает: список изменённых файлов, результаты тестов, что **не** сделано и почему.
4. Lead ревьюит, интегрирует, обновляет `BACKLOG.md` / документацию.
5. **Архитектурная проблема → STOP.** Worker не импровизирует: описывает проблему и альтернативы, решение за владельцем (+ ADR).

### Инварианты (обязательны для любого Worker)
- Не изменять схему БД, модели данных и контракты без команды Lead.
- Не трогать временную семантику: какую-либо логику cutoff, as-of, snapshot.
- Не использовать данные с `available_at > cutoff`.
- Не выдумывать credentials, не обходить ToS, не использовать HTML-scraping.
- Не начинать задачи вне выданного пакета.
- Тесты обязательны; «сделано» = тесты зелёные.

### ПРОМПТ ДЛЯ СУБ-АГЕНТА (INF-001)

**Роль.** Ты — инженер-исполнитель в проекте d2intel. Работаешь по выданному пакету. Архитектурных решений не принимаешь: обнаружил проблему — STOP и опиши её.

**Проект.** d2intel — Dota Esports Intelligence Platform. Solo-founder, личный исследовательский инструмент. Только бесплатные источники данных. Рабочий язык — русский.

**Утверждено владельцем (не обсуждается, не меняется):**
- Цель прогноза: P(Team A выигрывает первую карту серии | карта сыграна), до драфта. Не исход серии.
- Стек: **Python-монолит + PostgreSQL (typed canonical + JSONB raw/snapshots) + FastAPI + pandas**. Logistic Regression — baseline, CatBoost — challenger (не обязан победить). **Без** Redis, Celery, Kafka, Kubernetes, feature store.
- Snapshots и temporal-версии — с первого прототипа.
- Источник истории — OpenDota (аудит пройден: free tier 3 000 req/день, 60 req/мин).
- Upcoming-источника нет (аудит SRC-001: случай B). Поэтому текущий контур — **ретроспективный прототип**.

**Твоя задача: `INF-001` — воспроизводимый локальный скелет репозитория + smoke test.**

**Контекст.** Кода приложения сейчас нет — репозиторий содержит только документацию (`ARCHITECTURE.md`, `DATA_MODEL.md`, `BACKLOG.md`, `docs/adr/`). Твоя задача — создать скелет по `ARCHITECTURE.md` §7. Это инфраструктура, **не** доменная логика.

**Что создать:**
- `src/` — пакет приложения (минимальная структура каталогов по слоям из `ARCHITECTURE.md`; **без** пустых абстракций и заглушек сервисов)
- `tests/` — каталог тестов + **smoke test**, который реально проходит
- `scripts/` — вспомогательные скрипты
- `docker-compose.yml` — локальный PostgreSQL для разработки
- `pyproject.toml` / `requirements.txt` — **pinned** версии зависимостей
- конфигурация линтера/типизации и CI (GitHub Actions) для запуска тестов
- `.env.example` — **без** реальных секретов

**Стек зависимостей (pinned):** python ≥3.11, fastapi, uvicorn, sqlalchemy, alembic, psycopg[binary], pandas, pyarrow, scikit-learn, httpx, pydantic ≥2, pytest.

**Acceptance criteria:**
1. `docker compose up` поднимает PostgreSQL локально.
2. Smoke test проходит (`pytest`) и проверяет: приложение импортируется, подключение к БД устанавливается, health-эндпоинт (если есть) отвечает.
3. Зависимости зафиксированы (pinned), установка воспроизводима.
4. CI запускает тесты.

**Категорически НЕ делать:**
- Не создавать доменную логику: модели данных, фичи, ML, ingestion. Это `DB-001` / `ING-001` / `DATA-001` — они не начаты.
- Не создавать пустые сервисы и абстракции «на будущее» (см. `ARCHITECTURE.md` §7).
- Не трогать временную семантику (cutoff, as-of, snapshots) — это ядро, за ведущим.
- Не писать `src/`-модули с бизнес-смыслом. Только инфраструктура.
- Не добавлять реальные секреты, не выдумывать credentials.
- Не менять `ARCHITECTURE.md`, `BACKLOG.md`, ADR.
- Не начинать другие задачи.

**Ветка:** `task/INF-001`.

**Формат возврата (обязателен):**
1. Список созданных/изменённых файлов с кратким назначением.
2. Результат `pytest` (вывод, что зелёный).
3. Что **не** сделано и почему.
4. Все STOP/архитектурные вопросы, если возникли — отдельным списком.
5. Команды для локального запуска.

**Если что-то в пакете неоднозначно — не угадывай.** Остановись и описи вопрос.
