## План (порядок важен)

1. **Обновить данные.** Дотащить ingestion до свежих матчей. Курсор
   движется назад — надо начать с первой страницы без курсора (она самая
   свежая) и идти вниз `less_than_match_id` до пересечения с уже известным
   курсором из `ingestion_cursor`. Не ударь квоту (60/мин, 3000/день):
   свежее — это probably 1–3 страницы. Проверь результат по
   `max(event_time)` в `game` — должно стать ~2026-09-26.
2. **Нормализация:** `python scripts/normalize_once.py`. Часть серий
   уйдёт в карантин `incomplete_series` — это нормально для ещё не доигранных
   серий; в canonical попадают только завершённые карты.
3. **Получить фикстуру у владельца.** Владелец должен назвать конкретный
   матч (две команды, желательно время). Без этого двигаться нельзя —
   upstream-источника нет (вердикт B).
4. **Построить features с `cutoff = now`** для названных команд (через
   `PriorFormBuilder` с фильтром по сериям этих команд или прямой сборкой
   `team_form`), применить LR из артефакта.
5. **Записать prediction** с `evaluation_mode = 'prospective_observed'`,
   `cutoff_at = now`. Исход (`y`) неизвестен — в `prediction_evaluation`
   пишется `y = NULL` до тех пор, пока матч не доиграют.
6. **После матча** (когда результат появится в БД) — досчитать метрики и
   честно отчитаться: попал/не попал, какой порог, какой CI.

## Главный блокер, который надо решить с владельцем

Схема (`prediction`) требует `target_game_id` XOR `target_series_id`, оба с
FK на существующие строки (`prediction_target_xor`). У **будущего** матча
нет ни игры, ни серии — создавать фейковую canonical-запись нельзя
(загрязнит данные). Варианты, которые владелец должен выбрать:

- **(A) Расширить схему**: разрешить prospective-цель без FK (новая
  миграция + проектная запись). Это правильно, но это отдельная задача с
  своим ADR — не делай молча.
- **(B) Не писать в canonical prediction-таблицу**, а выдать предикт как
  research-артефакт (JSON/отчёт в `docs/`), честно маркируя
  `prospective_observed`. Без изменения схемы, но без immutable-провенанса.
- **(C) Гибрид**: записать prediction после того, как матч доигран и
  появился в БД, но **cutoff и features зафиксировать до результата**
  (сериализовать features + p_a в отдельный immutable файл до матча, потом
  связать). Хранит провенанс, не требует FK «в будущее».

Моя рекомендация — **(C)**, но решение за владельцем. Не приступай к
записи, пока он не выбрал.

## Чего делать нельзя (правила проекта)

- Не использовать данные с `available_at > cutoff`. Финальная статистика и
  фактический ростер матча — не pre-match признаки.
- Не обходить ToS/доступ, не скрапить Liquipedia.
- Не включать автозапуск/расписание ingestion — только ручные запуски.
- Не фабриковать данные; unknown ≠ 0.
- Не пушить токены/секреты в Git; токен PandaScore из чата скомпрометирован
  и не используется.
- Перед изменением рабочей БД — план и резервная копия; `downgrade base` и
  деструктивные тесты запрещены на рабочей БД (только `d2intel_test`).
