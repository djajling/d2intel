## 1. Пять временных полей

Каждая **версия** любой записи (raw, canonical, derived, snapshot) несёт временной конверт.
Поля не дублируют друг друга: это три разные шкалы времени плюс две метки обработки.

| Поле | Шкала | Определение | Может быть NULL |
|---|---|---|---|
| `event_time` (+ `valid_from`, `valid_to`) | игровой мир | когда факт произошёл / интервал, в который факт действовал | да, с причиной |
| `source_published_at` | часы источника | когда источник **заявил** о публикации | да (неизвестно) |
| `observed_at` | наши часы | когда наш collector **фактически получил** эту версию | нет |
| `ingested_at` | наши часы | когда версия **записана** в БД | нет |
| `available_at` | наши часы | когда версия после необходимой обработки стала **доступна** prediction pipeline | нет |

**Почему это не одно поле:** время в игровом мире, время по часам источника и время в нашей
системе — независимые шкалы. Совпадение или расхождение между ними — **информация**, а не ошибка;
схлопывание их в одно поле уничтожает возможность доказать отсутствие утечки.

### Служебные поля конверта

| Поле | Определение |
|---|---|
| `system_from`, `system_to` | интервал, в который версия считалась актуальной в нашей системе; новая коррекция закрывает старую системную версию |
| `assumed_available_at` | оценка доступности для режима реконструкции (см. §3.2) |
| `lag_policy_version` | версия политики, по которой вычислен `assumed_available_at` |
| `cutoff_at` | граница информации **конкретного** forecast; не время будущего события |

### Общие правила

1. Все времена — UTC `timestamptz`. Исходная timezone и оригинальный timestamp сохраняются.
2. Неизвестное время — `NULL` + причина, **не** фиктивная полночь и не «сейчас».
3. Временной конверт обязателен для всех версионируемых записей; отсутствие поля — дефект схемы.

## 2. Инварианты порядка

Обязательные (проверяются constraint'ами в `DB-001`):

```
observed_at <= ingested_at <= available_at
system_from < system_to
```

Допустимые расхождения (не ошибка, но сигнал):

- `source_published_at` **не обязано** предшествовать `observed_at` — у источника свои часы.
  Если `source_published_at > observed_at` сверх допуска (`skew_tolerance`), запись идёт
  в карантин на разбор clock skew, а не молча принимается.
- `event_time` не сравнивается напрямую с системными часами без учёта timezone.

Запрещено:

- выставлять `observed_at` в прошлое для данных, фактически полученных сейчас;
- выводить `available_at` из `event_time` (это и есть подмена знания фактом).

## 3. Правило cutoff

### 3.1 Основное

```
все версии, использованные forecast, имеют available_at <= cutoff_at
```

`cutoff_at` = момент фиксации complete draft (см. `docs/PRD.md` §3.2).

### 3.2 Строгость достижима только проспективно

**Строгое `observed_at <= cutoff_at` достижимо только для проспективно архивированной
истории** — то есть когда система действительно получила и записала данные до cutoff.

Для исторически реконструированного датасета правило иное:

- `observed_at` = фактический retrieval **сейчас** (задним числом не выставляется);
- допустимость версии оценивается через `assumed_available_at`;
- `assumed_available_at` вычисляется по `lag_policy_version` — задокументированной и
  **версионированной** политике задержки;
- оценка режима реконструкции **всегда отделена** от реального point-in-time replay.

Следствия из `DATA_MODEL.md` §2, которые этим закрепляются:

- обнаруженный сейчас старый трансфер не становится известным модели «вчера»;
- прошлый roster «последние пять сыгравших» — **inference** из прошлых матчей, а не confirmed roster;
- сегодняшняя исправленная таблица (патчи, справочники) не заменяет прошлую без отметки версии.

### 3.3 Запреты до матча

Зафиксировано как часть семантики (не только схемы):

1. Финальная статистика карты (KDA, GPM, XPM, итог) недоступна до матча.
2. Фактический ростер целевой карты недоступен до матча — только `prior_known_roster` с `roster_status`.
3. Hero winrate / patch meta — только с as-of фильтром.
4. Backdating запрещён.

## 4. Неизменяемость снимков

Объекты: `FeatureSnapshot`, `PredictionSnapshot`, `ModelVersion`, `SnapshotEvidence`.

| Правило | Содержание |
|---|---|
| Append-only | `UPDATE` и `DELETE` по снимкам запрещены технически (триггеры/права в `DB-001`) |
| Исправление = новый снимок | ошибка исправляется новой записью со ссылкой на superseded, старая не перезаписывается |
| Идентичность содержимого | `content_hash` фиксирует payload; `state_hash` — состояние входов |
| Провенанс | снимок ссылается на `model_version_id`, `feature_snapshot_id` и фиксированные evidence refs, а не на mutable latest |
| Идемпотентность | повторный расчёт с теми же входами не создаёт новый снимок (`idempotency_key` unique) |
| Версионирование | `snapshot_seq` растёт в пределах `prediction_id` |

Снимок — это **доказательство того, что было известно и что было посчитано в конкретный момент**.
Подмена снимка задним числом делает невозможной честную оценку, поэтому immutability
является требованием первого прототипа, а не «MVP 2» (см. `ADR-005`).

## 5. Словарь меток

| Метка | Значение | Разрешено ли называть «тогдашним прогнозом» |
|---|---|---|
| `retrospective_reconstructed` | датасет/прогноз построен сейчас на исторических данных; `available_at` — assumed по `lag_policy_version` | **НЕТ** |
| `prospective_observed` | данные реально накоплены системой до cutoff; `available_at <= cutoff_at` выполнено фактически | да |

**Расхождение терминологии, зафиксированное здесь:** черновик карточки `PRD-003` использовал
метку `prospective_archived`; утверждённый `docs/PRD.md` §2 использует `prospective_observed`.
Принят термин **`prospective_observed`** как утверждённый владельцем. `prospective_archived`
считается устаревшим синонимом и в коде не используется.

Метка обязательна: запись без метки режима не попадает в eval-когорту.

Дополнительные состояния (из `docs/PRD.md` §4): `excluded` (forfeit / void / walkover / карта
не сыграна), `quarantine` (неоднозначный `map_number`), `abstention` (неоднозначный статус драфта).

## 6. Маски доступности для обучения (train availability masks)

Обучающая когорта формируется **только** из записей, для которых:

1. `available_at <= cutoff_at` (или `assumed_available_at <= cutoff_at` с обязательной меткой `retrospective_reconstructed`);
2. режим помечен (`retrospective_reconstructed` / `prospective_observed`);
3. целевой исход размечен (`y = 1/0`; `excluded` и `quarantine` в обучение не идут с явной причиной);
4. отсутствуют критические нарушения purity (порог: **0**, см. гейт `G-PURITY`);
5. каноническая идентичность разрешена однозначно (порог unmapped в eval: **0**).

Каждая исключённая запись несёт `exclusion_reason`. Исключения без причины не допускаются.

**Режим реконструкции и prospective-режим оцениваются раздельно.** Смешивание их в одну
цифру качества запрещено: это сделало бы ретроспективу неотличимой от реального
point-in-time прогноза — ровно то, чего этот документ призван не допустить.

## 7. Проверка на примерах (тесты спецификации)

| Сценарий | Ожидаемое поведение |
|---|---|
| (а) raw пришёл позже события | `observed_at > event_time` — нормально; `available_at` не выводится из `event_time` |
| (б) опубликовано позже, чем стало доступно | `source_published_at > available_at` — допустимо, если расхождение в пределах `skew_tolerance`; иначе карантин |
| (в) снимок построен сегодня на матч прошлого года | метка `retrospective_reconstructed`; `observed_at` = сейчас; `assumed_available_at` по `lag_policy_version`; в отчёте явно отделено от prospective |
