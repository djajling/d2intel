# NORMALIZATION.md — правила нормализации исторического ядра (DATA-001)

**Статус:** реализовано (`src/d2intel/normalize/*`, миграция `0003`)
**Основание:** `BACKLOG.md` → `DATA-001`; `DATA_MODEL.md` §2–§4; `docs/PRD_TEMPORAL.md`;
`docs/research/OPENDOTA_API_MAP.md` §3, §5
**Кому нужно:** всем, кто читает canonical-слой и спорит о том, что считается map1

---

## 1. Что нормализуется и из чего

Вход — **только** raw-слой, записанный `ING-001`. Сеть не используется.

| Этап | Источник | Что создаёт |
|---|---|---|
| 1. Патчи | `raw_payload.endpoint_kind = 'patch_constants'` | `patch` |
| 2. Серии и карты | `endpoint_kind = 'pro_matches'` | `tournament`, `team`, `series`, `game`, `game_team` |
| 3. Участники | `endpoint_kind = 'match_detail'` | `player`, `game_participant`, `player_performance`, `roster_membership` |

Порядок этапов задан зависимостью: участники требуют уже существующей карты,
а карта требует контекста серии (иначе номер карты неопределён).

Привязка к raw идёт через `source_observation`: каждая запись страницы имеет
собственное наблюдение (`provider_entity_id = match_id`), именно оно становится
`source_observation_id` canonical-строки.

---

## 2. Каноническая идентичность

`canonical_id = uuid5(NAMESPACE, "<source>:<kind>:<external_id>")`, где
`NAMESPACE = uuid5(NAMESPACE_URL, "https://github.com/djajling/d2intel")`.

Свойства:

* **стабильность** — повторная загрузка того же `team_id`/`account_id`/`leagueid`
  даёт тот же uuid, без «поиска похожей записи»;
* **идемпотентность** — вставка с известным PK гасится `ON CONFLICT`;
* **различение источников** — внешний id уникален только внутри источника,
  поэтому источник входит в ключ.

Имена команд приходят из `radiant_name`/`dire_name` и могут отсутствовать: тогда
`canonical_name = NULL` и `identity_status = 'unresolved'` — схема это требует
(`team_name_or_unresolved`). Синтетические подписи не подставляются.
У игроков канонического имени нет вовсе: только `account_id`, статус
`unresolved`; отображение прозвищ — отдельная задача.

Межисточниковые конфликты (одна команда — два внешних id) **не разрешаются
автоматически**: это `DB-002`. Здесь маппинг всегда 1:1 в пределах источника.

---

## 3. Временной конверт canonical-записи

| Поле | Значение |
|---|---|
| `event_time` | старт карты; у команд/игроков/лиг — `NULL` |
| `source_published_at` | `NULL` (источник не заявляет время публикации) |
| `observed_at` | время наблюдения источника — берётся из `source_observation` |
| `ingested_at` | момент записи canonical-строки |
| `available_at` | `= ingested_at`: canonical доступна после записи |

Расхождение часов (`observed_at > ingested_at`) не исправляется в обратную
сторону: `ingested_at` поднимается до `observed_at`.

## 4. Серия и номер карты (map index)

Источник не хранит номер карты: `map_number` — порядковый номер матча внутри
`series_id` по возрастанию `start_time` (`OPENDOTA_API_MAP.md` §5.1).

**Группировка.** `series_id > 0` → ключ `series:<id>`.
`series_id = 0/None` → ключ `standalone:<match_id>`: такие матчи **не**
объединяются, иначе все одиночные матчи пары склеились бы в одну серию.

**Формат.** `series_type`: 0 → Bo1, 1 → Bo3, 2 → Bo5.

### Когда номер карты НЕ присваивается (`MAP_INDEX_POLICY_VERSION = map-index.v1`)

| Причина | Условие |
|---|---|
| `missing_team_identity` | нет `radiant_team_id` или `dire_team_id` |
| `unknown_series_type` | `series_type` вне 0/1/2 |
| `incomplete_series` | наблюдаемых карт меньше, чем требует формат |
| `series_count_exceeds_format` | наблюдаемых карт больше, чем допускает формат |
| `ambiguous_map_order` | совпадающее или неизвестное `start_time` внутри серии |
| `inconsistent_series_teams` | внутри одной серии разные пары команд |

Ключевое следствие: **неполная серия не получает номеров карт**. При обратном
обходе истории (descending `match_id`) пропущенные карты — ранние, поэтому
«первая найденная запись» не обязана быть map1. Угадывание запрещено.

Неоднозначная карта **не удаляется**: она пишется в `game` с
`map_number = NULL` и статусом `map_index_unresolved` плюс строка
`normalization_quarantine`. Данные сохранены, но в датасет map1 не попадают.
Когда недостающие карты приезжают, номера назначаются, а карантин закрывается
(`status = 'resolved'`).

**Что не делается:** remake (`attempt_number > 1`) не распознаётся — надёжного
признака в источнике нет, угадывать по близости времени старта нельзя.
Счёт серии не заполняется: источник его не даёт, вычисление — отдельная задача.

## 5. Ростер как свидетельство

`roster_membership` — одна строка на `(команда, игрок, карта)`:
`membership_type = 'actual_observed'`, интервал `[начало карты, конец карты)`,
ссылка на наблюдение-источник и `evidence` с политикой
(`ROSTER_POLICY_VERSION = roster-evidence.v1`).

Это **наблюдение**, а не «текущий состав»: строк не бывает «обновлённой
сегодняшней пятёркой». Объединение свидетельств в подтверждённые интервалы
состава требует заявленных составов из другого источника и здесь не делается —
inference «последние пять сыгравших» за confirmed roster не выдаётся
(`DATA_MODEL.md` §2).

---

## 6. Финальная статистика отделена

`player_performance` — отдельная таблица с маркером `data_class`
(`final` | `partial`) и `metric_schema_version`. В pre-match слое читается
`game_participant`, у которого колонок статистики нет вообще. Смешивать их в
одной mutable таблице `current_stats` запрещено (`DATA_MODEL.md` §4).
Проверка отсутствия утечки через агрегаты — `DB-003`.

---

## 7. Патчи

Справочник `/constants/patch` нормализуется в `patch`: граница патча — начало
следующего, у последнего интервал открыт. Тип (`major`/`minor`/`hotfix`)
выводится из метки детерминированно: буквенный суффикс → hotfix, `*.0` → major,
иначе minor; неизвестный формат → `NULL`.
Патч карты — последний с `effective_from <= start_time`. Фактический патч из
`/matches/{id}` приоритетнее, когда он доступен (для bulk-истории его нет).

---

## 8. Идемпотентность

Правило: **первая запись выигрывает**, существующие строки не перезаписываются.
Повторный прогон на неизменном raw создаёт ноль строк и ноль карантинных записей.

Единственное исключение — **дозаполнение** `game.map_number`, `game.status`,
`game.patch_id`: `NULL → значение`, один раз, никогда наоборот. Без него серия,
приехавшая неполной, навсегда осталась бы без номера карты.

## 9. Сознательные границы DATA-001

| Не сделано | Почему |
|---|---|
| `Match` и `TournamentStage` | в источнике истории нет stage-информации и будущих матчей; пустой слой без writer'а не создаётся |
| `Draft` / `picks_bans` | стадия 2 по `DATA_MODEL.md`; пустой `draft_timings` не влияет на нормализацию игр, карт и составов |
| Разрешение межисточниковых конфликтов | `DB-002` |
| Счёт серии, remake, stand-in | нет надёжного признака в источнике |
| Stand-in и роли | источник их не даёт; поля оставлены `NULL` |

## 10. Запуск

```bash
export DATABASE_URL=postgresql+psycopg://d2intel:d2intel_dev@localhost:5432/d2intel
python scripts/normalize_once.py            # отчёт по созданным строкам и карантину
```

Скрипт читает уже записанный raw: сначала `scripts/ingest_opendota_once.py`,
затем нормализация.
