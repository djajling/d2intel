# ADR-006 — Цель прогноза и фаза расчёта: pre-draft или post-draft

**Статус:** Accepted — вердикт владельца 2026-09-26: **вариант C**, порядок фаз
**Gate-1 = pre-draft / карта 1 (MVP) → Gate-2 = post-draft / карта N** (проспективный
Gate-2 — только после G-LIVE). Реализация вердикта: `docs/PRD.md` v1 (§1 — две фазы,
§3 п.2 — cutoff по гейтам, §5 — G-OPS-знаменатели, закрытый список
target_type/phase_contract, запись в revision log).

## Контекст

Два набора документов задают **разные цели прогноза**, и оба считаются действующими.

**Версия «первая карта до драфта» (корневые документы, пакет 2026-09-16):**

- `PRODUCT.md:32` — «Почему первая карта: не нужны будущие драфты… Предматчевый прогноз всей
  BO3/BO5 — другой target; он добавляется в MVP 2».
- `PRODUCT.md:34` — «Время cutoff — время решения на реально полученном состоянии, пока источник
  подтверждает **pre-draft**. Если статус сомнителен или драфт уже мог начаться, система
  воздерживается».
- `PRODUCT.md:41` — MVP: «первая карта… **не live, не драфтовая модель**».
- `PRODUCT.md:55` — «target: **первая карта**»; `PRODUCT.md:72` — «покрытие пригодным
  **pre-draft** прогнозом ≥90% на 30 последовательных eligible **game1** fixtures».
- `BACKLOG.md` §1 п.6 — «победа Team A на **ПЕРВОЙ КАРТЕ**… **до драфта**; это **НЕ series win**…
  Вероятность серии — отдельная задача **MVP2**».
- `BACKLOG.md` PRD-001 §CONTEXT — то же; `FIRST_10_TASKS.md` §2 (пакет 2026-09-16) —
  «цель, первая карта, правила cutoff».

**Версия «карта N после драфта» (owner-approved):**

- `docs/PRD.md:10` — «Единица прогноза: `P(Team A выигрывает карту N | карта N сыграна, полный
  драфт завершён)`».
- `docs/PRD.md:14` — «Момент расчёта: **после полного драфта**… Частичный драфт → abstention».
- `docs/PRD.md:16–28` — серийная вероятность **входит в scope** как производная (не MVP2).
- `docs/PRD.md:58` — «`cutoff_at` = момент фиксации **complete draft**».
- `docs/PRD.md:89` — G-OPS: 30 последовательных eligible **game** fixtures (без «game1»).
- `docs/PRD.md:3` — статус: **«Утверждён владельцем (2026-09-21)»**, следующая точка входа SRC-001.

Различие не косметическое: у версий **разные момент расчёта, входные данные, набор фич и
знаменатель гейтов**. На момент написания ADR `README.md` дополнительно утверждал, что
«владелец ещё не одобрял ни target первой карты, ни stack, ни gates», — это было
устаревшим относительно PRD-001 и с тех пор исправлено.

**Что уже не спорно** (менять не нужно): контракт и модель данных допускают обе версии —
`ARCHITECTURE.md:100` требует в ответе `target_type` и `forecast_phase` («нельзя выдавать значение
без указания target: первая карта или серия»), `DATA_MODEL.md:115` фиксирует у Prediction
`target_type, target_id, … horizon/phase contract`. Открыт вопрос **не формы, а того, какая
цель закрывается первым gate'ом**.

## Ключевое следствие, которое нужно учесть при выборе

Post-draft цель **ретроспективно воспроизводима** (драфт завершённой карты есть в parsed-данных
OpenDota) — то есть прототип на истории возможен без live-фида. Но для **проспективного**
продукта («открыть предстоящую встречу») post-draft прогноз требует ingest драфта в реальном
времени: драфт фиксируется за минуты до старта карты. Это делает G-LIVE
(`docs/PRD.md:93`, «Pro-live feed: coverage + rights + payload parity») **жёсткой зависимостью**
цели, а не отдельным поздним эпиком. Pre-draft цель такой зависимости не имеет.

Второе следствие: pre-draft цель не может использовать фичи целевого драфта —
`BACKLOG.md:716` прямо фиксирует, что пул героев неизвестен до драфта. Post-draft цель, наоборот,
получает драфт как входной сигнал, то есть это **другая модель**, а не тот же расчёт с другой меткой.

## Варианты

**A. Принять PRD-001 как есть** — post-draft, карта N, производная вероятность серии в MVP.
Привести `PRODUCT.md`, `BACKLOG.md §1 п.6`, `FIRST_10_TASKS.md`, `README.md:35` в соответствие.
*Плюсы:* owner-approved документ становится единственным источником истины; покрытие всех карт,
а не только первых; серийная вероятность получается бесплатно (чистая математика).
*Минусы:* проспективный продукт становится near-real-time и наследует G-LIVE; набор фич меняется
на драфтовый; меняется знаменатель G-OPS; «не драфтовая модель» из `PRODUCT.md:41` перестаёт быть верным.

**B. Вернуть pre-draft, первую карту** — переписать `docs/PRD.md` §1, §3.2, §5 и убрать
производную серийную вероятность в MVP2. *Плюсы:* совпадает с уже собранным UI-прототипом
(`ILLUSTRATIVE HERO POOL / NOT A DRAFT`, Game 1) и с «ретроспективный прототип на реальных
game1»; нет live-зависимости; минимальная цена изменения. *Минусы:* PRD-001 придётся
пересматривать после того, как он уже был утверждён; теряется карта N.

**C. Поддержать обе цели явно через `target_type` + `forecast_phase`** — MVP закрывает
pre-draft/карта 1 как первый gate, post-draft/карта N — отдельным вторым gate'ом со своим
датасетом, фичами и знаменателем. *Плюсы:* не остаётся молчаливой двусмысленности (именно этого
требует `ARCHITECTURE.md:100`); каждый target проверяется независимо; поставка инкрементальна.
*Минусы:* два набора гейтов и два датасета — больше спецификации до первой строки кода; нужен
явный порядок приоритетов от владельца, иначе вариант вырождается в «не решили».

## Рекомендация

Вариант **C с фиксированным порядком**: сначала pre-draft/карта 1 (совпадает с уже собранным
ретроспективным прототипом, не тянет live-фид, минимальный риск), затем post-draft/карта N как
отдельный gate с явной зависимостью от G-LIVE. Если владелец предпочитает одну цель без
двухфазности — вариант **B** как минимальное изменение, а не A, потому что A требует
одновременно переписать фичи, знаменатель гейтов и проспективную архитектуру до того, как
пройден SRC-001.

**Рекомендация принята владельцем 2026-09-26 (вариант C с указанным порядком).**

Дополнительные аргументы вердикта (срез 2026-09-26): в `/matches/{id}` OpenDota
`draft_timings` пуст (`docs/research/OPENDOTA_API_MAP.md:41`), порядок пиков/банов — только
через `/explorer` (клиент/валидатор есть, ingestion-раннера нет); по вердикту SRC-002
легального upcoming-источника нет, поэтому honest prospective-проверка сейчас возможна только
для pre-draft цели (ручной freeze → reconcile); замеренный pre-draft baseline — accuracy
0.5649 при floor 0.5191 (n=131).

## Последствия

- Выбранный target фиксируется в `docs/PRD.md` как единственный для MVP, а проигравший вариант
  остаётся явно записанным как MVP2 — без «переименования карты в серию».
- `PRODUCT.md:32` уже предусматривает этот путь: «Если владелец выбирает series win с первого
  дня, потребуется пересмотреть PRD-001, dataset и первые задачи». Пересмотр — часть этой задачи,
  а не отдельная инициатива.
- До вердикта моковый контракт прототипа остаётся `retrospective_reconstructed` и продолжает
  маркировать пул героев как «NOT A DRAFT» — он не должен молча «переехать» на post-draft семантику.

## Приёмка

1. Владелец выбирает A / B / C и, если C, порядок фаз. — **Выполнено 2026-09-26: C,
   Gate-1 pre-draft/карта 1 → Gate-2 post-draft/карта N.**
2. `docs/PRD.md` §1 и §3.2 приведены в соответствие выбору; при B/A — отдельная запись в
   revision log PRD-001 с датой. — **Выполнено: PRD v1, revision log 2026-09-26.**
3. `PRODUCT.md`, `BACKLOG.md §1 п.6`, `FIRST_10_TASKS.md`, `README.md` больше не
   противоречат `docs/PRD.md`; контрольный вопрос «что именно предсказываем и в какой момент»
   имеет один ответ во всех документах. — **Выполнено 2026-09-26.**
4. `target_type` и `forecast_phase` перечислены закрытым списком значений, и для каждого указан
   свой gate-владелец и знаменатель G-OPS. — **Выполнено: закрытый список в PRD §1.**
5. Если выбран post-draft: явно зафиксировано, что G-LIVE — предварительное условие
   проспективного продукта, а не поздний эпик. — **Выполнено: PRD §1 Gate-2.**
