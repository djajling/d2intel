## Роль

Ты — инженер-исполнитель в проекте **d2intel**. Получаешь одну задачу с жёсткими границами. Архитектурных решений не принимаешь: обнаружил неоднозначность или проблему — **STOP**, опиши её и жди решения.

Рабочий язык — **русский**.

## Контекст проекта

**d2intel** — Dota Esports Intelligence Platform. Solo-founder проект, **личный исследовательский инструмент** (не публичный сервис, без перепродажи данных). Главный принцип: «минимально необходимая сложность при максимальной проверяемости результата».

Центральный слой — вероятностный прогноз исхода с **сохранением того, что было известно на момент прогноза**, и последующей проверкой результата. Ключевой differentiator — собственная история «что было известно → что предсказано → что произошло».

**Только бесплатные источники данных.** Платные данные не входят в critical path. LLM — для неструктурированных данных и объяснений, **не** как математический предиктор.

## Что уже утверждено владельцем (PRD-001 — не обсуждается, не меняется)

- **Цель прогноза:** P(Team A выигрывает первую карту серии | карта сыграна), до драфта. **Не** исход всей серии. Team A фиксируется по канонической идентичности при создании fixture, а не меняется вместе с Radiant/Dire.
- **Snapshots и temporal-версии — с первого прототипа**, а не в MVP 2.
- **Стек:** Python-монолит + PostgreSQL (typed canonical + JSONB raw/snapshots) + FastAPI + pandas. Logistic Regression — baseline, CatBoost — challenger (**не обязан победить**). **Без** Redis, Celery, Kafka, Kubernetes, feature store, MLflow.
- **Источники:** OpenDota history — основной. Liquipedia — условно, до access/rights/coverage gate. PandaScore — исключён до письменного разрешения.
- **First 10 tasks** = ретроспективный вертикальный срез, **не** полноценный pre-match MVP.

## Результаты аудита источников (SRC-001 — уже выполнен, не повторять)

- **Следствие:** работаем в **ретроспективном контуре**. Все прогнозы маркируются `retrospective_reconstructed`.

## Задача: INF-001

**Воспроизводимый локальный скелет репозитория + smoke test.** Это инфраструктура, **не** доменная логика.

**Зависимости выполнены:** `PRD-001` (утверждён), `SRC-001` (завершён). Приоритет P0.

### Что создать

| Артефакт | Требование |
|---|---|
| `docker-compose.yml` | Локальный PostgreSQL для разработки. Логически изолирует DB/API/worker, но deployment простой. |
| `src/` | Минимальный пакет приложения: инициализация, конфигурация, подключение к БД, health-эндпоинт. |
| `tests/` | Каталог тестов + **smoke test, который реально проходит**. |
| `scripts/` | Будущие одноразовые entrypoints (минимум). |
| Зависимости | **Pinned** (зафиксированные) версии; воспроизводимая установка. |
| Alembic | Настроить инфраструктуру миграций и **зафиксировать совместимые версии SQLAlchemy + Alembic** (это прямая задача INF-001). Сами миграции схемы — **не** писать (это `DB-001`). |
| Линтер/типизация + CI | GitHub Actions, запускающий тесты. |
| `.env.example` | **Без** реальных секретов. |

**Стек зависимостей (pinned):** Python ≥3.11, fastapi, uvicorn, sqlalchemy, alembic, psycopg[binary], pandas, pyarrow, scikit-learn, httpx, pydantic ≥2, pytest.

**Справочно — целевая структура репозитория** (из `ARCHITECTURE.md` §7, на будущее):

```text
dota-intelligence/
  README.md  PRODUCT.md  ARCHITECTURE.md  DATA_MODEL.md
  FEATURES.md  ML.md  EXPERT_ENGINE.md  LIVE.md  BACKTEST.md
  SOURCES.md  BACKLOG.md  FIRST_10_TASKS.md
  docker-compose.yml
  src/
    ingestion/ normalization/ features/ models/ prediction/
    experts/ live/ market/ backtest/ api/
  tests/
  frontend/                          # позднее, если выбран React
  scripts/

```

**Важно:** эта структура — цель, а не инструкция создать всё сразу. Сейчас создаётся минимум, необходимый для работающего smoke test.

### Acceptance criteria

1. `docker compose up` поднимает PostgreSQL локально.
2. `pytest` проходит (smoke test реально зелёный) и проверяет: приложение импортируется, подключение к БД устанавливается, health-эндпоинт отвечает.
3. Зависимости зафиксированы (pinned), установка воспроизводима из чистого окружения.
4. CI (GitHub Actions) запускает тесты.
5. Версии SQLAlchemy + Alembic зафиксированы и совместимы.

### Категорически НЕ делать

- **Не создавать доменную логику:** модели данных, фичи, ML, ingestion, prediction. Это `DB-001` / `ING-001` / `DATA-001` / `FEAT-001` / `ML-001` — они **не начаты**.
- **Не писать миграции схемы БД.** Инфраструктура Alembic — да; миграции — нет (`DB-001`).
- **Не создавать пустые сервисы и абстракции Future заранее.** В частности **не** создавать пустые каталоги `experts/`, `live/`, `market/`, `backtest/`, `frontend/` — это Future-слои за своими гейтами. Границы модулей нужны для заменяемости источников и контроля leakage, а не для микросервисов.
- **Не трогать временную семантику:** cutoff, as-of, snapshots. Это ядро проекта, оно за ведущим архитектором.
- **Не добавлять реальные секреты**, не выдумывать credentials, не обходить ToS, не использовать HTML-scraping.
- **Не менять** `ARCHITECTURE.md`, `PRODUCT.md`, `BACKLOG.md`, `FIRST_10_TASKS.md`, ADR.
- **Не начинать** другие задачи.
