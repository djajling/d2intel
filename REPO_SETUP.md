# REPO_SETUP.md — Git и локальное развёртывание

Актуализировано 2026-09-22. Репозиторий уже существует: `https://github.com/djajling/d2intel`, ветка `main`, видимость public на момент проверки. Не создавать другой remote и не менять видимость без решения владельца. Правила агентов — `AGENTS.md`, текущие факты и блокеры — `HANDOFF_PROMPT.md`.

## 1. Git и публикация

Все команды ниже выполняются из корня клона. Сначала проверить ветку, чужие изменения и remote:

```powershell
git status --short --branch
git remote -v
git fetch origin
git log -5 --oneline
```

Чистую рабочую копию `main` обновлять через `git pull --ff-only origin main`. При расхождении веток или незакоммиченных изменениях остановиться и согласовать интеграцию; не применять reset/force-push. Для параллельных агентов — отдельные ветки/worktree, один интегратор. Не менять глобальную Git identity; использовать существующую авторизацию. Токены не вставлять в команды, remote URL или документы.

После согласованной задачи: проверки → обновление handoff → просмотр diff → добавить только свои файлы → commit с понятным назначением (`docs:`, `fix:`, `feat:` или task ID) → push в согласованную ветку. Для прямого push в `main` требуется соответствующее согласование владельца. Подтвердить публикацию сравнением `git rev-parse HEAD` и `git ls-remote origin refs/heads/main`.

`.github/workflows/ci.yml` запускает ruff, mypy и pytest, **не деплоит на компьютер владельца**. Статус CI проверять отдельно.

## 2. Цель и предусловия запуска

- Компьютер владельца, Windows; API только `127.0.0.1:8000`, без публикации в интернет.
- Python по `pyproject.toml` — не ниже 3.11. CI проверяет 3.11; текущий локальный запуск проверен на 3.12.2.
- PostgreSQL с БД приложения и подходящей схемой. На текущем компьютере уже есть отдельная служба PostgreSQL 17.10 и схема `0003`; Docker для неё не требуется.
- Если подходящая БД **уже есть**, не запускать конкурирующий Compose на том же порту. Для новой среды предусмотрен `docker-compose.yml` с PostgreSQL 17.4: после установки/настройки Docker использовать `docker compose up -d`, дождаться healthy. Саму установку системного ПО согласовывать отдельно.
- `DATABASE_URL`, при необходимости `APP_NAME` и `DEBUG` задаются окружением процесса. `src/d2intel/config.py` **не читает `.env` автоматически**. Девелоперские дефолты совпадают с compose и годятся только для изолированного локального контура; не публиковать БД с ними.
- На другой машине доступ к Git не предоставляет доступ к БД или процессу владельца. Деплой выполняется агентом/пользователем с доступом именно к целевому компьютеру.

## 3. Установка зависимостей и схема

В новом клоне создать окружение. Если `.venv` существует и исправно, не пересоздавать его:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic heads
```

Проверять exit code каждого шага; после ошибки не переходить к следующему. Если схема уже на head, миграция не нужна. Для отстающей схемы сначала проверить diff миграций, резервную копию и разрешение изменения БД, затем выполнить `python -m alembic upgrade head` тем же Python из `.venv`. В этой сессии schema уже была `0003`, миграции не применялись.

**Никогда не делать `alembic downgrade base`, сброс БД или удаление Docker-тома на рабочей базе.**

## 4. Проверки

```powershell
.\.venv\Scripts\python.exe -m ruff check src tests scripts
.\.venv\Scripts\python.exe -m mypy src
.\.venv\Scripts\python.exe -m pytest tests/test_smoke.py
```

Полный suite (`python -m pytest` из `.venv`) запускается только с проверенным `D2INTEL_TEST_DATABASE_URL`, который указывает на **выделенную одноразовую тестовую БД**, не рабочую. Fixture `migrated_engine` делает downgrade до base: данные будут удалены. Не использовать чужую общую тестовую БД при параллельной работе агентов. Известные исходные lint/type ошибки и фактически выполненный subset зафиксированы в handoff; они не исчезают от успешного health.

## 5. Запуск, обновление и остановка API

Для наблюдаемого запуска в отдельном терминале, без reload:

```powershell
.\.venv\Scripts\python.exe -m uvicorn d2intel.app:app --host 127.0.0.1 --port 8000
```

Во втором терминале выполнить реальный HTTP-запрос:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/health' -TimeoutSec 5
```

Успех — HTTP 200, `status: ok`, `database: up`. HTTP 503 или занятый порт не считать успешным запуском. `/health` не проверяет готовность feature/model/data слоя. UI пока нет.

Для фонового процесса можно использовать PowerShell `Start-Process` с `-WindowStyle Hidden`, абсолютным путём к Python из `.venv`, `-WorkingDirectory` корня клона и перенаправлением stdout/stderr в игнорируемые `*.log`. Записать возвращённый PID локально; перед остановкой проверить PID, путь Python, командную строку и слушающий порт. Не останавливать все процессы Python или чужой процесс по одному совпадению порта.

Обновление runtime: проверить разрешение → остановить только подтверждённый процесс d2intel → обновить чистый клон до опубликованного коммита → установить изменившиеся зависимости → при необходимости согласованные миграции → проверки → запуск → HTTP health. Если менялись только документы, работающий код не требует перезапуска. При неудаче сообщить точное состояние; не менять рабочую БД ради «зелёного» результата.

Остановка запуска в терминале — Ctrl+C. Фоновый процесс останавливать только после проверки его принадлежности проекту. PostgreSQL-службу ради остановки API не трогать. Автозапуск после перезагрузки, Windows-служба и расписание ingestion **не настроены** и требуют отдельного решения.

## 6. Состояние передачи

После каждого изменения обновлять `HANDOFF_PROMPT.md`: выполненный scope, результаты проверок, исходный/runtime SHA, состояние БД, health, известные ограничения и следующий шаг. Не записывать токены, пароли, полные connection strings или приватные данные. Архивы старых инструкций не являются текущим статусом.
