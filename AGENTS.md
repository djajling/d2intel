# AGENTS.md — начало работы с d2intel

Эта инструкция действует для всего репозитория. Контекст чатов не требуется: решения, состояние и результаты работы должны оставаться в Git. Рабочий язык с владельцем — русский.

## Что прочитать при подключении

1. `HANDOFF_PROMPT.md` — актуальное состояние, разрешённый scope, результаты проверок, блокеры и следующий шаг.
2. `README.md` — навигация и назначение проекта; `REPO_SETUP.md` — Git, локальный запуск, обновление и остановка.
3. `FIRST_10_TASKS.md` и карточку назначенной задачи в `BACKLOG.md` — зависимости и критерии приёмки.
4. `docs/REPO_LAYOUT.md`, связанный код, тесты, принятые ADR и `docs/PRD_TEMPORAL.md` — перед изменениями соответствующего слоя.

**Не начинать заново выполненные задачи.** `HANDOFF.md`, `AGENT_INF001.md`, `AGENT_ING001.md` и INF-001-промпты в `docs/agent/` — исторические пакеты, а не актуальное назначение. Не копировать их ограничения на другие задачи. При конфликте сверять актуальную передачу, принятые решения, код и Git; неоднозначное продуктовое/архитектурное решение оставлять владельцу.

## Проект и границы

- Личный исследовательский инструмент для профессиональной Dota 2; только бесплатные разрешённые источники. Текущий контур ретроспективный, не live-прогноз.
- Python-монолит: пакет `src/d2intel/`, PostgreSQL, FastAPI, ingestion и `normalize`. Будущие каталоги не создавать без кода и задачи.
- Не использовать данные с `available_at > cutoff`; финальная статистика и фактический состав целевого матча не являются pre-match признаками.
- Не обходить доступ/ToS, не подменять отсутствующие данные выдуманными. Market — только ANALYSIS, без автоматических ставок.
- Не менять архитектуру, источник, временную семантику или продуктовый scope молча. STOP → проблема → варианты → решение владельца.
- Наличие backlog не разрешает автоматически выполнять его целиком. Работать только над назначенной задачей.

## Git и несколько агентов

- Репозиторий: `djajling/d2intel`, основная ветка `main`. До работы: `git status --short --branch`, `git fetch origin`, проверить последний коммит и чужие изменения.
- Для параллельной работы — отдельная ветка/worktree на задачу и один ответственный за интеграцию и деплой. Не работать нескольким агентам в одной рабочей копии/индексе Git.
- Назначение, исходный SHA, область файлов, ответственный, состояние и блокеры фиксировать в общей карточке задачи или handoff в Git. Локальная память агента и непереданный чат не считаются передачей.
- Перед push снова fetch. При новом remote-коммите — интегрировать без потери чужой работы и повторить затронутые проверки. Не делать force-push, reset чужих изменений или массовый `git add -A` без просмотра diff.
- Владелец разрешил прямой push в `main` для пакета передачи и локального запуска от 2026-09-22. Это не бессрочное разрешение на любые изменения, merge или архитектурные решения; для следующей задачи уточнять её границы.

## Что значит «завершено»

Владелец требует **commit + push + реальный локальный запуск/обновление приложения на своём компьютере**, а не только изменение файлов.

1. Выполнить назначенную задачу и соразмерные тесты. Полный gate: `ruff check src tests scripts`, `mypy src`, `pytest`; PostgreSQL-тесты — только в выделенной тестовой БД.
2. Проверить diff и отсутствие секретов. Обновить существующий `HANDOFF_PROMPT.md`, статус назначенной задачи и связанные инструкции.
3. Зафиксировать изменения в согласованной ветке и выполнить push. Подтвердить SHA в remote, а не только успешный локальный commit.
4. На компьютере владельца запустить/перезапустить соответствующую версию по `REPO_SETUP.md`; проверить реальный HTTP `/health`, соединение с БД и актуальность миграций. Документальная правка без изменения runtime не требует бессмысленного перезапуска.
5. Проверить CI, если доступно. Не выдавать локальные тесты за результат GitHub Actions. Запуск процесса не доказывает готовность всего продукта.
6. В отчёте различать: код/документы опубликованы; проверки прошли/упали/не выполнялись; приложение запущено/не запущено; данные/функции готовы/не готовы. Блокер фиксировать явно — не объявлять весь scope Done.

## Деплой, данные и секреты

- Цель — **компьютер владельца, Windows**, только loopback. GitHub хранит код; push сам по себе не обновляет локальный процесс. Облачный агент не имеет автоматически доступа к этому компьютеру.
- Не ставить Docker/PostgreSQL заново, если уже есть подходящая рабочая БД. Не менять существующие службы, порты и базы без проверки.
- Перед изменением схемы рабочей БД — план и проверенная резервная копия. `alembic downgrade base`, удаление томов и разрушительные тесты запрещены на рабочей БД.
- Не включать автозапуск, расписание ingestion, публичный доступ или облачный хостинг без отдельного согласования.
- Никогда не записывать токены/пароли/ключи в Git, сообщения коммитов, отчёты, логи или handoff. Использовать защищённую авторизацию и переменные окружения; `.env` не коммитится и приложением автоматически не читается.
- Доступ, выданный одному агенту, не передаётся через документы. Следующий агент проверяет собственный доступ; токены из чатов не используются.

## Обязательное обновление передачи

В `HANDOFF_PROMPT.md` оставлять кратко: что изменено и почему; какой scope разрешён; какие файлы затронуты; команды и результаты проверок; runtime/миграция/способ запуска; блокеры; следующий шаг. SHA опубликованного коммита брать из Git. Для работающего приложения отдельно указывать версию runtime-кода, если документация была обновлена позже. Не хранить полный transcript и не плодить новые сводки вместо актуализации существующей.
